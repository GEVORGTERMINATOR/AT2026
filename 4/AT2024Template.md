# 1. Введение

## Цели
Документ определяет требования к системе мониторинга технологического оборудования. Он описывает возможности системы, включая как функциональные, так и нефункциональные требования, ограничения и интерфейсы.

Данный документ предназначен для:
- Заказчиков - для проверки соответствия требований потребностям производства.
- Разработчиков - для создания на основе документа функционала системы.
- Тестировщиков - для создания сценариев тестирования и проверки соответствия системы требованиям.
- Персонала предприятия - для понимания принципов работы системы и ограничений при её эксплуатации.

## Границы применения
Разрабатываемое программное обеспечение является системой мониторинга технологического оборудования.
Система предназначена для повышения уровня контроля за работой технологического оборудования на производстве.
К области применения системы относятся:
- Сбор данных с датчиков, установленных на оборудовании.
- Привязка данных к конкретным единицам оборудования.
- Сравнение данных с нормативными значениями, соответствующими данному оборудованию.
- Определение режимов работы оборудования (нормальный, критический, аварийный).
- Объединение единиц оборудования в группы (узлы), поддержание многоуровневой иерархии.
- Графическое отображение параметров работы оборудования и иерархии узлов.
- Звуковое оповещение персонала о переходе оборудования в аварийный режим работы.
К области применения системы не относятся:
- Удаленное управление технологическим оборудованием.
- Поиск и хранение документации к оборудованию.

## Термины и аббревиатуры

| Термин / аббревиатура | Определение |
|---|---|
| Аварийный режим | Режим работы оборудования или узла, при котором значение хотя бы одного контролируемого параметра вышло за аварийный предел, установленный эксплуатационной документацией. Требует немедленного уведомления оператора, звуковой индикации и отображения на графическом представлении завода. |
| Аварийный режим Системы | Состояние самой Системы при потере связи с источником данных, отказе серверного компонента или ином нарушении штатного функционирования, при котором Система информирует оператора и сохраняет последние достоверные значения с соответствующей пометкой. |
| Агрегат | Функционально связанная совокупность единиц оборудования, например котло-турбинный агрегат «котёл — турбина — насос», рассматриваемая в Системе как отдельный узел дерева. |
| АРМ | Автоматизированное рабочее место — рабочее место оператора или специалиста, оснащённое средствами отображения и ввода данных. |
| БД | База данных — организованная совокупность данных, хранимая и обрабатываемая в Системе. |
| Графическое представление завода | Отображение иерархии узлов, агрегатов и единиц оборудования с указанием их текущего режима работы на экране Системы. Синоним — мнемосхема. |
| Группа цехов | Узел дерева, объединяющий несколько цехов и/или других узлов более высокого уровня. |
| Датчик | Средство измерений или измерительный преобразователь, предназначенный для получения значения физической величины и передачи её в Систему. |
| Дерево узлов | Иерархическая структура организации оборудования предприятия, в которой узлы могут включать в себя оборудование и другие узлы. Число уровней вложенности не ограничено. |
| Документация оборудования | Эксплуатационная, техническая или нормативная документация, определяющая допустимые пределы параметров и режимы работы оборудования. |
| Звуковая индикация | Подача звукового сигнала — сирены, прерывистого звука и т.п. — при возникновении аварийного режима или события, требующего немедленного внимания оператора. |
| Иерархия узлов | См. Дерево узлов. |
| Инициатор события | Параметр, датчик или узел, изменение состояния которого привело к регистрации события или переходу режима. |
| ИТ | Информационные технологии — совокупность методов и средств обработки, хранения и передачи информации. |
| Каскадный пересчёт режимов | Автоматический пересчёт режима всех вышележащих узлов дерева при переходе дочернего оборудования или узла в критический либо . |
| Корневой узел | Верхний узел дерева, соответствующий предприятию в целом; его режим определяется режимами всех входящих в него узлов и оборудования. |
| Котло-турбинный агрегат | Пример агрегата, включающего котёл, турбину и насос, функционально связанные в единый технологический комплекс. |
| Критический предел | Граничное значение параметра, при котором оборудование или узел переходит из нормального режима в критический. |
| Критический режим | Режим работы оборудования или узла, при котором значение параметра находится в расширенном диапазоне, но ещё не достигло аварийного предела. Требует повышенного контроля. |
| Мнемосхема | Графическое представление иерархии узлов и оборудования завода с цветовой индикацией текущего режима. |
| Мониторинг | Автоматизированный процесс сбора, обработки, хранения, отображения и анализа значений параметров технологического оборудования. |
| Наследование состояния | Правило, при котором при переходе дочернего оборудования или узла в критический либо  соответствующий режим устанавливается для всех вышестоящих узлов по дереву. |
| Нормальный режим | Режим работы, при котором значения всех контролируемых параметров находятся в пределах, установленных документацией оборудования. |
| Оборудование | Единица технологического оборудования предприятия: котёл, турбина, трубопровод, насос и т.п., имеющая набор датчиков. Может входить в агрегат и участвовать в каскадном пересчёте режимов. |
| ОС | Операционная система — системное ПО, обеспечивающее работу серверов и АРМ. |
| Параметр | Физическая величина, измеряемая датчиком: температура, давление, вибрация, расход, уровень и т.п. Для каждого параметра задаются границы нормального, критического и аварийного режимов на основе документации. |
| ПК | Персональный компьютер — вычислительная машина для работы пользователя. |
| ПО | Программное обеспечение — совокупность программ и данных для работы Системы. |
| Предел | Граничное значение параметра, разделяющее нормальный, критический и аварийный режимы работы. |
| Расширенный диапазон | Диапазон значений параметра между нормальным и аварийным пределами, соответствующий критическому режиму работы. |
| Режим настройки | Режим работы Системы, доступный уполномоченным пользователям, предназначенный для редактирования дерева узлов, справочников оборудования и датчиков, границ режимов. |
| Режим обслуживания | Режим работы Системы, предназначенный для проведения регламентных работ, обновления ПО и БД, при котором штатный мониторинг может быть временно ограничен. |
| Режим работы | Состояние оборудования или узла, определяемое по значениям контролируемых параметров: нормальный, критический или аварийный. |
| Резервирование | Применение дублирующих серверных компонентов, обеспечивающих сохранение работоспособности Системы при отказе основного компонента. |
| Система | Система мониторинга технологического оборудования, разрабатываемая в рамках настоящего проекта. Далее по тексту — Система. |
| Событие | Изменение состояния оборудования или узла, выход параметра за предел, срабатывание датчика или иной факт, регистрируемый Системой. |
| Справочник | Структурированный набор данных Системы: перечень оборудования, датчиков, границ режимов, узлов дерева. |
| СУБД | Система управления базами данных — ПО для создания, ведения и использования баз данных. |
| Тревога | Уведомление о событии, требующем внимания оператора, в том числе о критическом или аварийном режиме. |

# 2. Общее описание

## Описание изделия
- **Интерфейсы системы**:
  
  - Система представляет собой программный комплекс мониторинга состояния технологического оборудования промышленного предприятия и контроля режимов его работы. Система выполняет функции агрегации параметров, классификации режимов и каскадного пересчёта состояний по иерархии узлов.
  
  - Система взаимодействует со следующими внешними сущностями:
    
    - технологическое оборудование (котлы, турбины, трубопроводы, насосы и т.д.);
    - датчики — источники первичных параметров (температура, давление, вибрация, расход, уровень и др.);
    - контроллеры и шлюзы сбора данных, передающие значения датчиков в Систему;
    - документация на оборудование — источник границ режимов (нормальный, критический, аварийный);
    
  - Оборудование организуется в иерархическую структуру (дерево): единица оборудования → агрегат → цех → группа цехов → … → корневой узел предприятия. Глубина вложенности не ограничена. Добавление, изменение и удаление узлов выполняется вручную уполномоченными пользователями средствами Системы.

- **Интерфейсы пользователя**:
  
  - Система предоставляет следующие пользовательские интерфейсы:
    
    - графическая мнемосхема завода с цветовой индикацией режима каждого узла (нормальный / критический / аварийный);
    - интерфейс ручного создания и редактирования дерева узлов (агрегаты, цеха, группы цехов и выше);
    - интерфейс ведения справочника оборудования и датчиков — привязка датчиков к оборудованию, задание границ режимов на основе документации;
    - журнал событий — фиксация переходов режимов, времени, узла и параметра-инициатора;
    - интерфейс просмотра истории значений параметров за выбранный период;
    - средства звуковой индикации (сирена, звуковой сигнал) при переходе любого узла в аварийный режим.

  - Интерфейсы должны быть рассчитаны на операторов, технологов и настройщиков Системы и не требовать от них навыков программирования.

- **Интерфейсы аппаратных средств ЭВМ**:
  
  - Система функционирует на серверном оборудовании, размещённом в ИТ-инфраструктуре завода:
    
    - серверы приложений — обработка потока данных, классификация режимов, каскадный пересчёт;
    - серверы баз данных — хранение справочников, исторических данных и журналов событий;
    - АРМ операторов — рабочие станции с мониторами и средствами звукового оповещения;
    - шлюзы и контроллеры сбора данных — сопряжение с датчиками и промышленным оборудованием.

- **Интерфейсы программного обеспечения**:

  - Система должна интегрироваться со следующим программным обеспечением:
    
    - промышленные протоколы и OPC-серверы — для приёма данных с датчиков и контроллеров (OPC UA, Modbus, MQTT и др.);
    - СУБД — для хранения справочников, истории и журналов событий;
    - операционные системы серверов и АРМ операторов;
  
- **Интерфейсы коммуникаций**:

  - Система использует локальную вычислительную сеть предприятия и поддерживает:

    - промышленные протоколы (OPC UA, Modbus, MQTT);
    - сетевые протоколы (TCP/IP, HTTP/HTTPS);

- **Ограничения памяти**:
  
  - Объём хранимых данных определяется:

    - количеством единиц оборудования и датчиков;
    - частотой опроса датчиков;
    - глубиной хранения истории и журналов событий.

  - Система должна обеспечивать хранение исторических данных и журналов событий в течение срока, установленного регламентом предприятия, с возможностью архивации, выгрузки и очистки устаревших данных. При достижении порогов заполнения хранилища Система должна информировать обслуживающий персонал.
    
- **Действия**:
  
  - Система выполняет следующие основные действия:

    - сбор параметров с датчиков всего вида оборудования в непрерывном режиме;
    - классификацию режима каждой единицы оборудования по значениям датчиков и границам из документации (нормальный / критический / аварийный);
    - каскадный пересчёт режимов по дереву узлов: переход единицы оборудования в критический или аварийный режим переводит в тот же режим узел, в который она входит, и все вышележащие узлы вплоть до корневого;
    - визуализацию состояния завода — отображение режима каждого узла на мнемосхеме с цветовой индикацией;
    - звуковую индикацию при переходе любого узла в аварийный режим (сирена, звуковой сигнал);
    - журналирование событий — фиксация переходов режимов, времени, узла и параметра-инициатора;
    - ведение справочников — оборудования, датчиков, границ режимов, структуры узлов;
    - предоставление истории — просмотр значений параметров и событий за выбранный период.

  - Система работает в круглосуточном режиме. Предусматриваются основной режим, режим настройки (для уполномоченных пользователей), режим обслуживания и аварийный режим самой Системы — при потере связи с источником данных Система информирует оператора и сохраняет последние достоверные значения с соответствующей пометкой.

## Функции изделия
**Сбор данных:**
- Непрерывный прием показаний с разнородных датчиков, установленных на единицах оборудования, по стандартным протоколам.

**Оценка состояний по пороговым значениям:**
- Сопоставление текущих показаний с паспортными значениями и определение режима работы оборудования.

**Формирование иерархии:**
- Ручное построение и редактирование многоуровневого дерева технологических узлов с неограниченной глубиной вложенности.
- Автоматическое распространение статуса вверх по дереву: переход нижележащего агрегата в критический или аварийный режим влечет безусловный перевод всех связанных родительских узлов выше по иерархии в соответствующий режим.

**Оповещение и сигнализация:**
- Световая и звуковая индикация: оповещение через физические устройства в соответствии со статусом узлов.
- Графическое отображение предприятия с цветовой индикацией текущих состояний.

**Регистрация событий:**
- Фиксация всех фактов перехода между состояниями, времени подтверждения тревог оператором и сохранение истории показаний датчиков.

- **Задачи:** добавление новых типов оборудования и датчиков, управление доступом, мониторинг работоспособности самой системы.

## Ограничения
- **Регулирующая политика.** Система должна соответствовать стандартам отображения промышленной информации и правилам Ростехнадзора в части оперативного оповещения, но не требует прохождения жестких сертификаций для систем автоматической аварийной защиты.

- **Ограничения аппаратных средств ЭВМ.** Вычисления по агрегации статусов дерева должны выполняться на локальном сервере предприятия. Интерфейс диспетчера должен гарантированно функционировать на стандартных автоматизированных рабочих местах оператора завода с подключенной аудиосистемой.

- **Интерфейсы с другими приложениями.** Система должна бесшовно интегрироваться с контроллерами нижнего уровня через промышленные шлюзы, а также иметь API для передачи агрегированных статусов работы цехов в вышестоящую систему управления производством.

- **Параллельная работа.** Движок системы должен обеспечивать параллельную асинхронную обработку входящих потоков телеметрии от тысяч датчиков одновременно. Интерфейс должен поддерживать параллельную сессию работы для нескольких операторов.

- **Функции протоколирования.** Система обязана вести непрерывный, защищенный от редактирования журнал событий. Протоколированию подлежат: любые выходы датчиков за пределы нормы, факты включения/выключения сирены, действия операторов и изменения структуры дерева администратором.

- **Функции управления.** Управление конфигурацией (изменение структуры дерева, добавление датчиков, редактирование критических/аварийных порогов в документации) должно осуществляться исключительно через изолированный модуль администратора и быть заблокировано для операторов во время дежурства.

- **Требования к языкам высокого уровня.** Для обеспечения высокой производительности и параллельной обработки данных бэкенд системы должен быть реализован на языках высокого уровня с эффективным управлением памятью и потоками.

- **Протоколы интерфейсов синхронизации сигналов.** Обмен данными между датчиками/шлюзами и сервером должен использовать промышленные протоколы с обязательным подтверждением доставки пакетов и контролем качества связи.

- **Требования надежности.** Режим работы — 24/7/365. Допустимое время полной недоступности системы — не более 5 минут в год. Обязательно наличие горячего резервирования серверов и ежедневного резервного копирования базы данных конфигурации.

- **Критичность приложения.** Приложение классифицируется как критически важное для производства. Сбой в расчете состояний или задержка включения сирены могут привести к техногенной аварии, разрушению турбин/котлов и угрозе жизни персонала.

- **Соображения безопасности и секретности.** Система должна функционировать внутри закрытого сетевого контура завода, полностью изолированного от публичного Интернета. Должна быть внедрена ролевая модель доступа со строгой авторизацией. Все пароли и конфигурационные файлы шлюзов должны храниться в зашифрованном виде.

## Предположения и зависимости
1) Предполагается, что на автоматизированных рабочих местах операторов и серверах завода развернута и доступна ОС семейства Linux или актуальные версии Windows, поддерживающие выполнение современных высокоуровневых сред.

2) Система зависит от наличия на заводе развернутого сервера промышленных данных или шлюзов, которые агрегируют «сырые» сигналы с датчиков и отдают их в едином протоколе.

3) Предполагается, что существующая локальная кабельная и беспроводная сетевая инфраструктура завода обладает пропускной способностью не менее 100 Мбит/с и задержками до сервера не более 50 мс.

4) Предполагается, что физические автоматизированные рабочие места операторов оснащены исправными аудиокартами и внешними динамиками, а в операционной системе не заблокирован вывод звука.

5) Система зависит от предоставления заказчиком полного и актуального перечня технологических регламентов и паспортов оборудования с указанием точных диапазонов (норма/критический/авария) для каждого типа датчиков.

6) Предполагается, что исходная топология завода (список цехов, агрегатов и их связей) относительно стабильна, а новые узлы добавляются ручным оператором дискретно, а не в автоматическом динамическом потоке.

- **Обновление мнемосхемы.** Изменение режима узла должно появляться на мнемосхеме не позже чем через **2 секунды** после приёма значения параметра.
- **Реакция интерфейса.** Действия пользователя — открытие журнала событий, переключение между узлами, запрос истории — должны выполняться не дольше чем за **3 секунды** при штатной нагрузке.
- **Звуковая индикация.** Сирена или звуковой сигнал при переходе узла в аварийный режим должны включаться не позже чем через **1 секунду** с момента классификации режима.
- **Каскадный пересчёт.** Пересчёт режимов по дереву узлов должен занимать не более **1 секунды** независимо от глубины вложенности и числа вышележащих узлов.

### Пропускная способность

- **Датчики.** Система должна параллельно и асинхронно обрабатывать телеметрию не менее чем от **10 000 датчиков** одновременно с частотой опроса по технологическому регламенту.
- **Пользователи.** Система должна выдерживать одновременную работу не менее **20 сессий** операторов и специалистов без деградации времени отклика.
- **История и журналы.** Запись истории и журналов событий за период, установленный регламентом предприятия, не должна снижать производительность при чтении.

### Утилизация ресурсов

- **Процессор.** Загрузка ЦП серверов приложений при штатной нагрузке (10 000 датчиков, 20 сессий) — не более **70 %** в течение 95 % времени наблюдения.
- **Память.** Загрузка оперативной памяти серверов приложений и БД — не более **80 %** доступного объёма.
- **Резервирование.** При отказе одного резервируемого серверного компонента Система должна сохранять работоспособность и требования к времени отклика. Горячее резервирование, допустимое время недоступности — не более **5 минут в год**.
- **Хранилище.** При достижении порогов заполнения **80 %** и **95 %** Система должна информировать обслуживающий персонал, не прерывая сбор и обработку данных.

## Ремонтопригодность

### Резервное копирование и восстановление

- **Резервное копирование.** База данных конфигурации (справочники, границы режимов, дерево узлов) должна резервироваться автоматически **ежедневно**.
- **Восстановление.** Восстановление БД конфигурации из резервной копии с проверкой целостности — не более **1 часа**.
- **Архивация.** Должны быть предусмотрены архивация, выгрузка и очистка устаревших исторических данных и журналов событий.

### Диагностика и мониторинг состояния Системы

- **Самодиагностика.** Система должна самостоятельно проверять состояние компонентов — серверов приложений и БД, шлюзов сбора данных, каналов связи — и сообщать обслуживающему персоналу о неисправностях.
- **Потеря связи.** При потере связи с источником данных Система переходит в аварийный режим: информирует оператора и сохраняет последние достоверные значения с пометкой.
- **Журнал событий.** Журнал должен быть защищён от редактирования и фиксировать выходы датчиков за пределы нормы, включение и выключение сирены, действия операторов и изменения структуры дерева администратором.

### Обслуживание и обновление

- **Режим обслуживания.** Предусматривается режим обслуживания для регламентных работ, обновления ПО и БД с временным ограничением штатного мониторинга.
- **Обновление.** Обновление ПО и конфигурации не должно нарушать целостность исторических данных и журналов событий.
- **Замена компонента.** Отказавший резервируемый серверный компонент должен заменяться без остановки Системы (горячее резервирование); время переключения на резерв — не более **5 минут**.

### Доступность и время восстановления

- **Режим работы.** Система работает круглосуточно — **24/7/365**. Допустимое время полной недоступности — не более **5 минут в год**.
- **MTBF и MTTR.** 
  - **MTBF** — не менее **8 760 часов** (не чаще одного отказа в год), исходя из требования доступности 99,999 % и допустимого времени полной недоступности не более 5 минут в год.
  - **MTTR** для критичных компонентов (серверы приложений и БД, шлюзы сбора данных) — не более **30 минут** за счёт горячего резервирования и автоматического переключения.
  - **MTTR** для некритичных компонентов (АРМ оператора, вспомогательные сервисы) — не более **4 часов**.
  - Значения **MTBF** и **MTTR** согласованы между собой и с требованием доступности.
- **Процедуры обслуживания.** Должны быть документированы процедуры обслуживания серверного оборудования и АРМ, проверки средств звукового оповещения и действий при отказах аппаратных средств.

### Документирование обслуживания

- **Руководство администратора.** Управление учётными записями, ведение справочников, редактирование дерева узлов и границ режимов, резервное копирование и восстановление БД конфигурации.
- **Инструкция по эксплуатации технических средств.** Обслуживание серверов и АРМ, действия при отказах, проверка средств звукового оповещения.

Интеграция с источниками данных выполняется через промышленные шлюзы и OPC-серверы.

- **Ограничения по данным.** Система не выполняет функции поиска и хранения документации на оборудование. Актуальность и полнота переданных заказчиком технологических регламентов и паспортов оборудования с указанием точных диапазонов (норма / критический / авария) являются ответственностью заказчика. Система не несёт ответственности за некорректную классификацию режимов, вызванную ошибками во входных документах.

- **Технологические ограничения.** Система является системой мониторинга и оповещения. Она не выполняет функции удалённого управления технологическим оборудованием и не формирует управляющих воздействий на технологический процесс. Все решения о вмешательстве в технологический процесс принимаются оперативным персоналом на основании данных Системы и действующих регламентов.

- **Ограничения по среде функционирования.** Система функционирует внутри закрытого сетевого контура завода, полностью изолированного от публичного Интернета. Должна быть внедрена ролевая модель доступа со строгой авторизацией. Все пароли и конфигурационные файлы шлюзов хранятся в зашифрованном виде.

- **Ограничения по режиму работы.** Система работает в круглосуточном режиме (24/7/365). Предусматриваются основной режим, режим настройки (для уполномоченных пользователей), режим обслуживания и аварийный режим самой Системы. При потере связи с источником данных Система информирует оператора и сохраняет последние достоверные значения с соответствующей пометкой.

## Требования к пользовательской документации

- **Общие требования.** Пользовательская документация должна быть выполнена на русском языке, не содержать положений, допускающих неоднозначное толкование, и быть достаточной для освоения и правильной эксплуатации Системы персоналом соответствующей квалификации. Формат поставки — электронная версия; по запросу заказчика — печатный экземпляр в согласованном количестве.

- **Состав документации.** В комплект пользовательской документации должны входить:

    - **Руководство оператора** — содержит сведения о назначении Системы, условиях выполнения, порядке работы оператора при мониторинге оборудования, подтверждении тревог, работе со звуковой сигнализацией, а также тексты сообщений Системы и действия оператора при сбоях.

    - **Руководство администратора** — содержит инструкции по управлению учётными записями, ведению справочников оборудования и датчиков, редактированию дерева узлов и границ режимов, резервному копированию и восстановлению базы данных конфигурации.

    - **Инструкция по эксплуатации технических средств** — описывает порядок обслуживания серверного оборудования и АРМ, действия при отказах аппаратных средств, порядок проверки работоспособности средств звукового оповещения.

- **Требования к содержанию руководства оператора.** Руководство оператора должно отражать: назначение Системы, условия выполнения, выполнение программы, сообщения оператору. Дополнительно должны быть отражены: порядок действий при переходе узлов в критический и аварийный режим, порядок квитирования (подтверждения) тревог, правила работы с мнемосхемой завода, действия при потере связи с источником данных (аварийный режим Системы).

- **Требования к актуализации.** Документация должна быть актуализирована до ввода Системы в промышленную эксплуатацию по результатам пусконаладочных работ и испытаний. Пересмотр документации производится при внесении изменений в функциональность Системы. Актуальные версии документов должны быть доступны персоналу на рабочих местах в электронном виде.

- **Требования к доступности.** Руководство оператора должно находиться на АРМ оператора в электронном виде (ярлык на рабочем столе или встроенная справка). Полный комплект документации хранится у ответственного подразделения заказчика и в службе эксплуатации Системы.

## Используемые компоненты
Для развертывания и функционирования системы используются следующие покупные и готовые компоненты:
- **Датчики технологических параметров:** промышленные датчики температуры, давления, вибрации и расхода, оснащенные стандартными интерфейсами передачи данных.
- **Устройства сигнализации:** физические светозвуковые колонны, промышленные маяки и сирены с релейным или цифровым управлением.
- **Серверное оборудование:** стандартный сервер x86-64 для развертывания серверной части системы и базы данных.
- **Система управления базами данных (СУБД):** готовая реляционная СУБД для долговременного хранения истории телеметрии, журналов событий и конфигурации узлов.
- **Автоматизированные рабочие места (АРМ):** персональные компьютеры операторов, технологов и администратора, предназначенные для установки и запуска пользовательской части системы мониторинга.

## Интерфейсы

**Интерфейс пользователя**:
- **Графический интерфейс оператора:** интерактивная мнемосхема предприятия с цветовой индикацией статусов узлов, панель текущих тревог с кнопками подтверждения и всплывающими оповещениями.
- **Интерфейс инженера-технолога:** экраны построения графиков телеметрии по выбранным параметрам за заданный интервал времени, экран настройки и редактирования пороговых границ режимов.
- **Интерфейс системного администратора:** панель управления деревом технологических узлов (добавление, редактирование, перемещение), экраны привязки датчиков и настройки прав доступа пользователей.

**Аппаратные интерфейсы**:
- Подключение шлюзов сбора данных к промышленным датчикам через физические порты, аналоговые и дискретные входы или сетевой интерфейс.
- Дискретные выходы или сетевые контроллеры для подачи сигналов на внешние светозвуковые оповещатели и сирены.

**Программные интерфейсы**:
- Интерфейс взаимодействия с СУБД через стандартные протоколы и драйверы доступа к данным.
- Внутренний программный интерфейс для взаимодействия серверной части с клиентским интерфейсом в реальном времени.

**Интерфейсы коммуникаций**:
- Промышленные протоколы сбора телеметрии для непрерывного опроса показаний датчиков и контроллеров.
- Сетевые протоколы для защищенной передачи данных между сервером системы, рабочими станциями пользователей и периферийными устройствами по локальной сети предприятия.
